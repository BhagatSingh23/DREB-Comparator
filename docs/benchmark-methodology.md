# Benchmark Methodology

This document describes the benchmark methodology used in this framework, including
the single-machine framing, warmup protocol, statistical methodology, and
contamination prevention measures.

---

## Single-Machine Relative Comparison Framing

**All benchmark results from this framework are relative comparisons on a single
specific machine.** They are not absolute numbers transferable across machines.

Results must be interpreted as:
> "On this machine, under these conditions, Algorithm A achieved X% higher
> throughput than Algorithm B."

Not as:
> "Algorithm A achieves 1.5M ops/sec." (without machine context)

This framing is essential because:
- Absolute throughput depends on CPU clock speed, cache hierarchy, memory bandwidth
- JVM behavior (JIT compilation, GC) varies by vendor, version, and flags
- OS scheduler behavior affects thread timing and CPU measurements
- Other running processes introduce noise

Every result set includes a `metadata.json` that captures the exact machine
configuration, enabling readers to understand the environment and reproduce
the experiment on the same hardware.

## Warmup Protocol

### Why Warmup Matters
The JVM performs Just-In-Time (JIT) compilation and other optimizations during
the first invocations of code. Measuring a "cold" run captures JIT compilation
overhead rather than steady-state algorithm performance.

### Protocol
1. **Minimum 3 warmup runs** (configurable, higher for stress profiles)
2. Warmup runs execute the exact same workload and measurement procedure as
   measured runs
3. Warmup results are logged but **discarded** from the final statistics
4. All algorithms receive identical warmup treatment — never compare a cold
   run of one algorithm to a warmed-up run of another

### JMH Warmup
JMH benchmarks use their own warmup annotations (`@Warmup(iterations=3)`).
These are separate from the workload-simulator warmup.

## Statistical Methodology

### Per-Run Measurements
Each measured run produces:
- Throughput (ops/sec)
- Latency distribution (all individual `allow()` call latencies)
- Memory snapshot (before/after heap)
- CPU load samples
- Correctness violations
- Fairness index (for multi-client workloads)

### Aggregation Across Runs
For each algorithm × workload combination, we report:
- **Mean**: arithmetic mean of per-run values
- **Median**: middle value (robust to outliers)
- **Standard deviation**: spread of measurements
- **Min / Max**: range
- **Measurement runs**: minimum 5 (configurable)

### Latency Percentiles
Latency percentiles (p50, p90, p95, p99, max) are computed from the
**full sorted array** of individual measurements — no reservoir sampling,
no approximation. This provides exact percentiles at the cost of memory.

Formula for percentile p (0–100):
```
index = ceil(p / 100 × n) - 1
percentile = sorted_values[index]
```

### Throughput
```
throughput = totalOperations / durationSeconds (ops/sec)
```

## Contamination Prevention

### JIT Warmup
Addressed by the warmup protocol above.

### Garbage Collection
- `System.gc()` is called before each measured run with a brief pause
- This is best-effort — the JVM is not guaranteed to collect
- GC activity during runs is measured via JMH's `-prof gc` (for JMH benchmarks)
  and via `MemoryMetrics` (for workload benchmarks)
- Document: GC pauses can affect individual run latency; this is captured in
  max latency and p99

### Allocation Pressure
- No per-request object allocation in the hot measurement loop where avoidable
- `RateLimitRequest` objects are pre-generated by workloads before measurement
- `RateLimitResponse` objects are lightweight (4 fields, no collections)

### Logging Overhead
- **No per-request logging** during measured runs
- Logging is limited to pre-run and post-run aggregate messages
- SLF4J guards prevent string construction for disabled log levels

### Synchronization Overhead
- Algorithms use per-client synchronization, not global locks
- The benchmark measures the algorithm's actual synchronization cost as part of
  its performance — this is intentional, not contamination

### Thread Scheduling
- Virtual threads (JDK 21) are used for 1000+ client simulations
- Virtual threads have lower scheduling overhead than platform threads
- Platform threads are used for small client counts (2, 10, 100) where the
  overhead difference is negligible
- `CountDownLatch` ensures all client threads start simultaneously

### OS Noise
- Results include standard deviation to quantify run-to-run variation
- Multiple runs (minimum 5) provide statistical confidence
- Document: running benchmarks on a machine with other active workloads
  increases noise. Close unnecessary applications.

### File I/O
- No file I/O inside the `allow()` hot path
- Result writing happens after all measurements are complete

## Two Benchmark Pipelines

This framework has two complementary benchmark systems:

### 1. JMH Microbenchmarks (`src/jmh/java`)
- Measures raw `allow()` call throughput and latency
- Uses JMH's sophisticated warmup, forking, and measurement methodology
- Produces JMH JSON output
- Best for: comparing per-call overhead between algorithms

### 2. Workload Simulator (`BenchmarkRunner`)
- Measures algorithm behavior under realistic traffic patterns
- Includes multi-client simulation, fairness measurement, burst handling
- Produces CSV/JSON/PNG/Markdown output
- Best for: evaluating algorithm behavior in realistic scenarios

Both pipelines' results are merged into `processed/summary.csv` by
`ResultAggregator` for unified analysis.

## Reproducibility

See [reproducibility.md](reproducibility.md) for the full reproducibility protocol.

Key requirements:
- All randomized workloads use a seed stored in `metadata.json`
- Same seed produces the same logical event sequence
- Same machine + same seed + same config = same results (within noise)
- `metadata.json` captures all environmental variables

## Known Limitations

1. **CPU measurement**: `OperatingSystemMXBean.getProcessCpuLoad()` is a sampled
   metric with limited precision. It may not capture sub-millisecond CPU spikes.

2. **Memory measurement**: heap snapshots via `Runtime` are approximate. They
   capture total heap usage, not per-algorithm allocation. The per-client state
   size estimate divides total delta by client count — this assumes most
   allocation is per-client state.

3. **Virtual thread scheduling**: while virtual threads reduce scheduling
   overhead vs. platform threads, the JVM's virtual thread scheduler still
   introduces some non-determinism in thread interleaving.

4. **GC impact**: despite best-effort pre-run GC, the JVM may trigger GC during
   measured runs. This is reflected in max/p99 latency but can distort
   throughput measurements.

5. **Single-machine**: all results are specific to the benchmarking machine.
   Algorithm rankings may differ on different hardware (e.g., many-core server
   vs. laptop).
